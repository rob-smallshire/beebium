# PiEconetBridge AUN interop: an automated integration test programme

Beebium's AUN transport serves two first-class use cases: Beebium instances
talking to each other, on one host or across a LAN, and Beebium talking to
other AUN implementations. The first is well served today — mDNS peer discovery
exists precisely to make it configuration-free — and it is covered by the
existing Beebium-to-Beebium integration tests.

This document is about the second, and specifically about
[PiEconetBridge](https://github.com/cr12925/PiEconetBridge). Among the
non-Beebium peers we might meet it is the one that matters most: it is the most
actively developed AUN implementation, it is what sits between an emulated
station and a real Econet segment in practice, and it is the peer whose
behaviour our own stack has historically been least prepared for. Interop with
it should be a tested property, not an anecdote.

The obstacle has always looked like hardware. It is not. This document sets out
how to bring up a real PiEconetBridge in an integration test with no Pi, no
Econet HAT, and no kernel module, on any developer machine and in CI.

## The key enabling fact: the bridge does not need the wire

Two independent properties of the upstream project make a hardware-free bridge
possible, and both are supported configurations rather than workarounds.

**The userspace bridge builds separately from the kernel module.** The
top-level `Makefile` has distinct `build-module` and `build-utilities` targets;
only the former needs kernel headers. `econet-hpbridge` links against
`libpthread`, `libssl`/`libcrypto` and, optionally, `libexplain` — touching a
`.noexplain` marker file in `utilities/` drops the last of those. The header it
includes from the module tree, `include/econet-gpio-consumer.h`, is an ordinary
in-repo header, not a kernel one.

**A configuration with no wire is explicitly supported.** The kernel module is
reached only through a `WIRE NET n ON DEVICE /dev/econet-gpio` line. Omit it
and the networks the config defines become what upstream calls *Null* networks:
"one which can only have local emulation or distant AUN machines in it". That
is exactly the topology we want to test — a locally emulated fileserver, and
Beebium as a distant AUN machine.

The bridge is Linux-only regardless (`econet-hpbridge.c` includes
`<linux/if_tun.h>` for its IP gateway feature), so on macOS and Windows the
whole bridge runs in a container.

## Topology under test

```
   Beebium server (station 2.1)                PiEconetBridge (userspace only)
   ---------------------------                 ------------------------------
   --station 1                                 FILESERVER ON 1.254
   --aun net=2:port=32768                      EXPOSE HOST 1.254 ON PORT *:32768
   --aun map=1.254@<bridge>@32768   <-- UDP -->  AUN MAP HOST 2.1 ON <beebium> PORT 32768 NONE
   NFS 3.34 in a sideways slot                 (no WIRE NET line -> Null network)
```

Note the net numbering. PiEconetBridge requires every network number in its
config to be non-zero, and works out when to present 0 to a given medium. Our
`--aun net=N` parameter is the matching self-declaration on our side. The guest
addresses the fileserver as `1.254` — a non-zero net, so it passes through
`AunBackend`'s net-0 translation unchanged — while frames the bridge sends us
arrive for net 2 and are presented to the guest as net 0, its own segment. The
test therefore exercises the net-translation path in both directions, which
Beebium-to-Beebium testing on a flat net-0 cloud never does.

The `NONE` qualifier on `AUN MAP HOST` is deliberate. Upstream also offers
`AUTOACK`, where the bridge acks our data traffic itself to suppress the
duplicate transmissions emulators tend to produce. Running with `NONE` means
acks are generated by the actual endpoint, which is both the stricter test and
the configuration under which ack timing is observable. A later scenario should
pin `AUTOACK` behaviour too, since real deployments use it.

## What the tests are for

These are not smoke tests. Each scenario targets a specific claim in
`docs/discussion/aun-robustness.md` that is currently either unverified or
verified in the wrong direction.

### Tier 1 — the transaction works at all

1. **Login.** Boot with NFS, `*NET`, `*I AM 1.254 SYST`, assert the
   fileserver's response on screen. This is the baseline the rest depend on,
   and it is the first automated proof that our four-way synthesis satisfies a
   non-Beebium peer. **Built, and passing** with a flat net-0 declaration:
   login and `*CAT` complete against a real bridge with every reply
   acknowledged.

   Its sibling — the identical scenario with `--aun net=` set to the net the
   bridge knows us by — failed, and led straight to defect 8 in
   `aun-robustness.md`. That defect is now fixed and the test passes; it stays
   as the regression test. That the very first interop test found a defect no
   amount of Beebium-to-Beebium testing could reach is the argument for this
   whole programme, made earlier than expected.
2. **Catalogue and file transfer.** `*CAT`, then load a file large enough to
   span multiple data frames. Exercises the scout-extra split, the byte
   trickle, and repeated back-to-back transactions through the idle cooldown.
3. **Broadcast.** A bridge-originated broadcast reaches the guest; a
   guest-originated broadcast reaches the bridge.

### Tier 2 — the robustness defects

These are the reason to build the harness, and they need traffic Beebium cannot
generate against itself.

4. **Reply overtaking its ack.** With the bridge as peer, run a login loop and
   assert that every iteration completes. This is the scenario in which
   `FourWayHandshake` destroys a reply that arrives while it is waiting for an
   ack; it appears intermittently and correlates with load, so the test must
   iterate rather than run once. Once the holding queue lands, this test should
   go from flaky-under-load to solid, and a counter of parked-then-redelivered
   frames should be non-zero — assert on that counter, not just on absence of
   failure, so the test cannot pass vacuously.
5. **Third-station traffic during a transaction.** Add a second AUN endpoint
   (a second Beebium, or a scripted UDP peer) that transmits to us while we are
   mid-transaction with the fileserver. Assert its frame is eventually
   delivered to the guest rather than destroyed.
6. **Inbound immediate during a transaction.** Drive a MachinePeek at the
   guest while it is mid-transaction and assert a reply comes back.
7. **Transmission to a station that is not there.** Address a station the
   bridge knows nothing about and assert the guest sees a failure — not
   `&00 Transmitted OK`. This is the acceptance test for defect 2 and it
   currently cannot pass.
8. **Bridge stopped mid-session.** Kill the bridge process during a
   transaction and assert the guest recovers to a usable state within a bounded
   time, rather than hanging or reporting phantom success.

### Tier 3 — load

9. **Sustained login loop.** Several hundred iterations, asserting both
   completion and that wall-clock throughput does not collapse. The blocking
   `sendto` (defect 4) is most likely to show itself here, as is any unbounded
   growth in the holding queue.

## Reproducing the defects: three instruments, not one

A real bridge is a fidelity anchor but a poor reproducer. It reorders packets
only under load, non-deterministically, and it cannot be asked to emit a NAK on
demand. A test that waits for a race to happen is a flaky test. The two jobs —
*is our behaviour correct against a real peer* and *does this specific defect
still bite* — need different tools, in the same way the Piconet work separated
`FakePiconetDevice` from the `[piconet-hardware]` contract suite (see
`docs/discussion/piconet-feasibility.md`, "The Fidelity Trap").

**1. The real bridge — conformance.** Tier 1 and tier 3 above. Answers "does a
genuine, independently written AUN implementation get on with us?". Realistic,
non-deterministic, and the only instrument that can find problems we have not
thought to model.

**2. A perturbation proxy — deterministic ordering faults.** *Confirmed
necessary by measurement:* 25 login/`*CAT`/`*BYE` iterations against a real
containerised bridge produced a holding-queue count of exactly zero — held,
redelivered, expired and dropped all nil. On a loopback path nothing reorders,
so the scenario that motivated the whole programme does not occur naturally.
Without deliberate perturbation, tier 2 scenario 4 can only ever be a smoke
test. A small UDP relay
sitting between Beebium and the real bridge, holding and reordering datagrams
under test control: "delay the next Ack until one further datagram has passed",
"drop exactly one Ack", "duplicate this datagram". The traffic is genuine
bridge traffic; only its arrival order is ours to choose. This is the right
reproducer for defect 1, because it exercises the real conversation with the
race made deterministic, and it turns an intermittent load-dependent symptom
into a test that fails every time.

**3. A synthetic AUN peer — cases the bridge will not produce on demand.** A
scripted endpoint speaking raw AUN packets, for the situations a well-behaved
bridge simply will not generate when asked: an unsolicited NAK, traffic from a
third station timed precisely inside our transaction, an immediate arriving
mid-handshake, a reply to a station that never asked. Cheap to write — the AUN
header is eight bytes — and fully deterministic. Scenarios 5, 6 and 7 belong
here.

Below all three sits the cheapest layer, which is where most of the *regression*
tests should end up: `TestBackend` at the `FourWayHandshake` seam, injecting
out-of-order frames directly with no sockets involved. The integration tests
prove the unit tests model reality correctly; the unit tests are what keep the
fix from regressing at commit speed.

## Observability is test infrastructure, not a feature

Every tier-2 scenario fails the same way from the outside: the guest does not
get its reply. Without frame-level visibility, each of these tests reports
"login did not complete" and leaves the diagnosis to a human with a packet
capture. That makes the suite expensive to own and easy to start ignoring.

Two pieces of instrumentation should therefore land as part of the harness
rather than after it:

- **`SubscribeEconetEvents`** (defect 5 in `aun-robustness.md`) — currently
  `UNIMPLEMENTED`. Frame send/receive, handshake stage transitions, and drops
  with a reason. Built as an `ObservableBackend` decorator in the chain, as
  already designed. This is the single most useful thing we can add before
  writing any of these tests.
- **Counters on `FourWayHandshake`** — frames parked, redelivered, expired,
  dropped for want of queue space; synthetic acks issued. Exposed through the
  existing diagnostic accessors. These let a test assert on the mechanism
  rather than only on the outcome, so it cannot pass vacuously once the fix
  lands.

## Sequencing

Deliberately infrastructure-first. No production behaviour changes until a test
can demonstrate the change was needed.

1. **Bridge fixture** — container image, native path, config rendering,
   readiness, teardown, diagnostics. Prove it with tier 1 scenario 1 and
   nothing else.
2. **Observability** — `SubscribeEconetEvents` and the handshake counters, so
   later failures are readable.
3. **Rest of tier 1** — establishes the baseline the robustness work is
   measured against, and shakes out fixture flakiness on scenarios that should
   pass today.
4. **Perturbation proxy and synthetic peer.**
5. **Tier 2 as red tests.** Each defect gets a failing test before any fix.
   Scenario 7 should fail immediately and unambiguously; scenario 4 should fail
   reliably through the proxy.
6. **Fix, one defect at a time**, each turning its own red test green.
   `tests/test_four_way_handshake.cpp:855` — which currently asserts that an
   out-of-order Unicast is correctly discarded — gets inverted as part of the
   defect-1 fix. That inversion is the clearest single marker that the fix has
   landed.
7. **Tier 3** last, once the behaviour is correct and there is something worth
   measuring.

## Harness design

Follow the existing `integration_tests/` convention: a `uv`-managed pytest
project with its own `pyproject.toml` depending on the in-repo Beebium Python
client, fixtures in `conftest.py`, tests marked `slow` and skipped by default.
`integration_tests/l3fs/` is the closest model — it already launches two
Beebium servers and drives them through the client — so
`integration_tests/pieb-aun/` should read as a sibling of it.

The new element is a `bridge` fixture with two interchangeable
implementations behind one interface, selected by platform and by an
environment override:

- **Native.** On Linux with a built `econet-hpbridge` available (via
  `BEEBIUM_PIEB_BIN`, or a checkout at `BEEBIUM_PIEB_SRC` built on demand),
  run it directly as a subprocess with a generated config in a temporary
  directory. Fastest inner loop for a developer on Linux.
- **Container.** Everywhere else, and in CI, run it in Docker. The fixture
  builds or pulls the image, starts the container, and waits for readiness.

The interface both provide is the same: an address and port the bridge answers
AUN on, a fileserver station number, a way to generate the config, log capture,
and a clean stop. Tests never learn which one they got.

Practical points the fixture must handle:

- **Addressing between host and container — the hard part.** Measured, not
  assumed: Docker Desktop's published-port forwarder rewrites **both** the
  source address and the source port of host-to-container UDP. A datagram sent
  from the host's port 45454 to `127.0.0.1:39999` arrives in the container from
  `192.168.65.1:55981`. The rewritten port is stable for the life of a flow but
  is not knowable before the first datagram is sent.

  This is fatal to any static peer configuration, because AUN peers are matched
  by `(address, port)` at *both* ends — PiEconetBridge's `AUN MAP HOST` and
  Beebium's `AunBackend` reverse map alike. A `AUN MAP HOST 2.1 ON
  host.docker.internal PORT <our port>` entry cannot match traffic arriving
  from the NAT, and the bridge logs `Traffic received from unknown source ...
  Unable to allocate dynamic host` and drops it.

  Two paths follow:

  - **Clean path (Linux):** `--network host`. No NAT, the static `AUN MAP HOST`
    entry matches, and our station identity is pinned by configuration. This is
    the stricter arrangement and the one CI should run.
  - **NAT'd path (Docker Desktop):** add upstream's `DYNAMIC <net> NONE` to the
    bridge config. A dynamic net is upstream's own answer to an unrecognised
    AUN source: the bridge allocates a station for it on first contact. The
    return direction needs nothing special, because replies traverse the same
    forwarder in reverse and reach Beebium from the published address and port
    it already has in its peer map.

  The fixture picks between them; tests are unaffected. The cost of the NAT'd
  path is that our station number is bridge-assigned rather than declared,
  which is a small loss of fidelity in exchange for a working developer loop on
  macOS. A future option, and the better one for both platforms, is to run a
  Linux Beebium in a sibling container on the same user-defined network, so
  there is no NAT in the path at all and the gRPC control channel — being TCP —
  does not care that it is forwarded.
- **Port allocation.** Bind Beebium's AUN port from an ephemeral range chosen
  by the fixture and interpolate it into the bridge config, so parallel runs
  and leftover sockets do not collide. The bridge's own listener can stay on
  32768 inside its own container or namespace.
- **Readiness.** Do not sleep. Poll until the bridge's UDP listener answers, or
  until its log announces the fileserver is up, with a timeout.
- **Fileserver state.** Each test session gets a fresh filestore directory —
  password file, a `SYST` user, and one or two fixture files for the transfer
  test — built into a temporary tree the container mounts. Never reuse a
  developer's real filestore.
- **Diagnostics.** On failure, dump the bridge's log, the Beebium server's
  stderr, and — once it exists — the frame-level event stream. Without the
  bridge log these failures are very hard to read.

### Container image

A small Dockerfile alongside the existing `docker/linux-ci` and
`docker/linux-bundle` images, from the same `ubuntu:24.04` base for
consistency. It clones PiEconetBridge at a pinned commit, touches
`utilities/.noexplain`, runs `make build-utilities`, and sets an entrypoint
that renders the config from environment variables and execs the bridge in the
foreground. Deliberately *not* `make install` — that path wants systemd, udev
rules, a group, and `/etc/econet-gpio`; we want one binary and one config file.

Pin the upstream commit in the Dockerfile and record it in this document. An
unpinned bridge turns every upstream change into a mystery CI failure. Bumping
the pin should be a deliberate commit, and a good moment to re-read the
upstream changelog for protocol-affecting changes.

Whether the bridge needs to run as root without the wire is unverified — the
upstream install path makes it setuid for GPIO access, which we do not use, and
its AUN ports are all above 1024. Assume unprivileged, confirm during the
first spike, and record the answer here.

## CI

Run the whole programme on Linux, where it is cheapest — the native fixture on
the standard runner, and at least one job through the container fixture so the
container path does not rot. On macOS and Windows runners, run tier 1 only if
at all; the value there is proving the fixture works on a developer's machine,
not repeating coverage.

Treat these as a scheduled and pre-release gate rather than a per-commit one,
alongside the other `slow` integration tests. Tier 2 in particular is the sort
of test that only earns its keep if a failure is taken seriously, which argues
for a small, well-understood set that runs reliably over a large set that
people learn to ignore.

## Why this is worth the apparatus

Everything in tiers 2 and 3 is invisible to Beebium-to-Beebium testing — not
because that configuration matters less, but because both ends of it are built
from the same assumptions. Two Beebium instances ack promptly, do not interleave
unrelated traffic into someone else's transaction, never send a negative
acknowledgement, and on loopback never reorder. A conforming peer is entitled to
do all of those things, and a real bridge does; that is where our stack's
optimism gets found out. The two suites are complementary: Beebium-to-Beebium
proves the configuration users reach for first, this one proves the assumptions
underneath it.

There is also a standing reason to keep this suite honest in the other
direction: the mDNS peer-discovery schema was designed to be adoptable by other
AUN implementations, PiEconetBridge among them. If that ever happens, this
harness is where we would prove it works.
